## 1. Требования, из которых исходим

| Требование | Значение | Влияние на архитектуру |
|---|---|---|
| Доступность | 99,9% (≈ 8,8 ч/год) | Multi-AZ, автоматический фейловер, health checks |
| RTO | 45 мин | Автопромоут реплики БД, active-active приложений |
| RPO | 15 мин | Синхронная реплика (RPO≈0) + WAL-архив (PITR ≤15 мин) |

| Объём данных | 50 ГБ | Шардирование не нужно |
| Нагрузка | поиск 50 RPS, оформление 10 RPS | Умеренная — горизонтальное масштабирование stateless-слоя |

## 2. Стратегия масштабирования: вертикальное vs горизонтальное

**Выбор: горизонтальное для слоя приложений, вертикальное + реплики для БД.**

- **Приложения (core-app, client-info, ins-product-aggregator, ins-comp-settlement)** — stateless,
  масштабируются **горизонтально** через HPA (см. Task 2). Плюсы: нет простоя при масштабировании,
  нет потолка одной ВМ, реплики разносятся по зонам и дают отказоустойчивость «бесплатно».
- **PostgreSQL** — stateful, масштабируется **вертикально** (ресурсы хоста) + **read-реплики** для
  разгрузки чтения (поиск продуктов/тарифов). Горизонтальная запись (шардинг) не требуется.
- **Кэш (Redis)** снимает нагрузку чтения каталога продуктов/тарифов и сессий с БД.
- **CDN** снимает нагрузку статики и выравнивает latency по регионам.

Горизонтальное масштабирование эффективнее для наших нагрузок: пики (реклама, всплеск поиска)
поглощаются добавлением подов, а в спокойное время реплики сворачиваются — высокая утилизация ресурсов.

## 3. Зоны доступности

Разворачиваем в **одном регионе Yandex Cloud (ru-central1) в трёх зонах доступности** (A, B, D),
режим **active-active**.

Почему не мультирегион: объём данных 50 ГБ и низкий RPS не оправдывают сложность межрегиональной
репликации и связанных проблем консистентности. Требования 99,9% / RTO 45 / RPO 15 полностью
покрываются тремя зонами внутри региона. Географическая latency решается CDN (см. п.6), а не
переносом БД ближе к пользователю. Три зоны (а не две) нужны для кворума Patroni и переживания
отказа одной зоны без потери кворума.

---

## 4. (a) Конфигурация Kubernetes — один растянутый кластер

**Решение: один растянутый региональный кластер Managed Service for Kubernetes.**

- Control plane (master) — **региональный**, реплицирован в 3 зонах → HA управляющего слоя.
- Worker-узлы организованы в **node-группы по одной на зону**; поды сервисов разносятся между зонами
  через `podAntiAffinity` / `topologySpreadConstraints`.

Почему растянутый, а не независимые кластеры на площадку:
- Зоны одного региона связаны сетью с задержкой **<1–2 мс** — кросс-зональное взаимодействие дешёвое.
- Единый кластер = единый деплой, единый ingress/service mesh, единый мониторинг — проще эксплуатация.
- Региональный master сам по себе даёт отказоустойчивость control plane.

Независимые кластеры на каждую площадку оправданы **только для мультирегиона** (высокая latency,
изоляция отказов, суверенность данных), что в нашем сценарии не требуется.

---

## 5. (b) Балансировка нагрузки и health checks

Слои балансировки (сверху вниз):

1. **Yandex Cloud DNS** — точка входа, health-checked записи, гео-маршрутизация.
2. **CDN** — статика, отдаётся с ближайшего к пользователю PoP.
3. **Application Load Balancer (L7)** — публичный вход для динамики; распределяет трафик между
   зональными target-группами; **health checks** (`GET /health`, `GET /ready`) на уровне подов —
   нездоровые поды/зоны исключаются из ротации.
4. **API Gateway для B2B-партнёров** — отдельный вход с **Rate Limiting**/квотами (проблема партнёра
   на 250 RPS решается здесь и в Task 6) и своими health checks.
5. Внутри кластера — **Service + Ingress**, kube-proxy балансирует между подами.

Health check явно отражены на схеме стрелками ALB → node-группы каждой зоны.

---

## 6. (c) Фейловер-стратегия на уровне «клиент ↔ приложение»

- Приложения работают **active-active в 3 зонах**. Клиентский запрос через DNS→ALB попадает в любую
  живую зону.
- **Отказ зоны:** health check ALB перестаёт проходить → зона выводится из ротации, трафик
  автоматически перетекает в две оставшиеся зоны. Клиент отказа не замечает.
- **Отказ primary БД:** Patroni автоматически промоутит синхронную реплику; приложения переподключаются
  через **connection pooler** (PgBouncer/Odyssey) по кластерному FQDN — код приложения не меняется.
- Результат: RTO измеряется минутами (≪ 45 мин), деградации доступности клиент практически не видит.

Отражено на схеме на уровне взаимодействия клиента с ALB и переключения на живые зоны.

---

## 7. (d) Конфигурация базы данных

**Managed Service for PostgreSQL, HA-кластер на фреймворке Patroni.**

- **Топология:** 1 primary + 2 реплики, по одному хосту в каждой из 3 зон.
- **Репликация:** синхронная минимум на одну реплику (**RPO ≈ 0**) + асинхронная на вторую.
- **Резервное копирование:** ежедневные полные бэкапы + непрерывный **WAL-архив в Object Storage**
  (S3-совместимое) → **Point-in-Time Recovery** с гранулярностью, удовлетворяющей **RPO ≤ 15 мин**.
- **Фейловер:** автоматический промоут реплики (Patroni) → **RTO — единицы минут**.
- **Доступ:** через connection pooler; read-реплики используются для разгрузки чтения (поиск).
- Каждый сервис по-прежнему держит свою схему в общем кластере (как сейчас).

Фреймворк конфигурации кластера (**Patroni**) отражён на схеме.

---

## 8. Шардирование БД

**Не применяем.**

Обоснование: объём данных 50 ГБ и низкий RPS (поиск 50 / оформление 10) не создают проблемы, которую
решает шардирование; его сложность (роутинг, кросс-шардовые запросы, ребалансировка) не оправдана.
Масштаб чтения обеспечивается read-репликами и Redis-кэшем, статики — CDN. К вопросу шардирования
стоит вернуться при росте объёма до единиц ТБ или при упоре в вертикальный предел primary.
Решение отражено комментарием на схеме.

## 9. Итоговый стек (Yandex Cloud)

| Компонент | Сервис | Роль |
|---|---|---|
| Вход/DNS | Cloud DNS | гео-маршрутизация, health checks |
| Статика/латентность | CDN | кэш на PoP по РФ |
| Балансировка | Application Load Balancer (L7) | health checks, active-active |
| API партнёров | API Gateway | Rate Limiting, квоты |
| Оркестрация | Managed Kubernetes (региональный) | один растянутый кластер, 3 зоны |
| Кэш | Managed Redis | каталог/тарифы/сессии |
| БД | Managed PostgreSQL (Patroni) | 1 primary + 2 реплики, 3 зоны |
| Бэкапы | Object Storage | WAL-архив, PITR, origin статики |
