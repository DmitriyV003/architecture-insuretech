# Task 4. Проектирование продажи ОСАГО — решения

## Бизнес-требования
- Клиент заполняет заявку с данными авто → сервис запрашивает предложения у всех страховых.
- Предложение каждой страховой показывается на экране **сразу, как только пришло**.
- Максимальное ожидание решения от страховой — **60 секунд**.
- Пик: до **2 500 одновременных** пользователей, создающих заявки.
- Страховые: однотипный REST с двумя эндпоинтами — «создать заявку», «получить предложение» (опрос).
- Ранее принято: выделить `osago-aggregator` (отправка заявок + опрос решений → передача в core-app);
  остальная логика ОСАГО остаётся в core-app.

## Пользовательский поток
1. Веб-приложение → `core-app`: `POST /osago/applications` (данные авто). REST, синхронный ответ
   `{ applicationId }`.
2. `core-app` → `osago-aggregator`: `POST /applications` (submit). Возвращает `202 Accepted`.
3. Веб-приложение открывает поток: `GET /osago/applications/{id}/offers/stream` — **SSE**.
4. `osago-aggregator` рассылает заявку во все страховые (create) и **опрашивает** решения (get offer),
   т.к. API страховых — «создать + получить» (пуша нет).
5. На каждое пришедшее предложение `osago-aggregator` публикует событие в топик `osago-offers`.
6. `core-app` (консьюмер, broadcast) получает событие и **сразу** пушит его в SSE-соединение клиента.
7. По истечении 60 c (Timeout) выдаётся терминальное событие `completed/timeout`, SSE закрывается.

## 1. Реализация osago-aggregator

### Нужно ли своё хранилище? — ДА
- Опрос решений идёт асинхронно до 60 с; нужно durable-состояние на каждую пару
  `(applicationId, страховая)`: отправлено / получено / таймаут / ошибка, курсор опроса.
- Сервис задеплоен в нескольких инстансах — состояние **нельзя** держать только в памяти одного пода
  (падение пода = потеря заявок в опросе).
- Нужна корреляция ответов страховых с заявкой и дедупликация.
- **Решение:** собственная схема PostgreSQL (`osago_aggregator`) для состояния заявок/опросов.
  Опционально Redis — для горячего состояния и счётчиков rate-limit.

### Какой API он предоставляет core-app?
- **Синхронный REST (команда):** `POST /applications` — принять заявку (данные авто, `applicationId`,
  список целевых страховых), поставить в работу, вернуть `202 Accepted`. Идемпотентность по
  `Idempotency-Key` = `applicationId`.
- **Асинхронно (результаты):** предложения публикуются событиями в топик `osago-offers`
  (по одному событию на предложение) — core-app их консьюмит. Пуш отдельных предложений по REST
  синхронно невозможен (это стрим), поэтому — события.
- (Опц.) `GET /applications/{id}/offers` — реконсиляция/фолбэк-опрос, если стрим прервался.

## 2. Интеграция core-app ↔ osago-aggregator
- **Submit:** REST `POST /applications`. Быстрый синхронный ACK, идемпотентность, обёрнут
  **Timeout + Retry** (безопасно из-за idempotency-key).
- **Результаты (предложения):** **события через Message Broker** (топик `osago-offers`). Причины:
  - согласуется с Event-Driven из Task 3 («сохранить подход»);
  - развязывает сервисы во времени и по нагрузке (2 500 пользователей × N страховых = много событий);
  - решает маршрутизацию к нужному инстансу core-app (см. п.5) через broadcast.

## 3. Интеграция web ↔ core-app (API для веб-приложения)
- **Submit заявки:** REST `POST /osago/applications` → `{ applicationId }`.
- **Поток предложений:** **Server-Sent Events (SSE)** — `GET .../offers/stream`. Новая стрелка на схеме
  (не REST). Почему SSE:
  - бизнес требует показывать каждое предложение **сразу** → нужен server→client push;
  - поток однонаправленный (сервер→клиент) → SSE проще и легче WebSocket;
  - работает поверх обычного HTTP/LB, авто-reconnect на стороне браузера.
- Альтернативы: WebSocket (избыточен, двунаправленный), long-polling (менее эффективен). Выбран SSE.

## 4. Паттерны отказоустойчивости — где и зачем

| Граница | Паттерны | Зачем |
|---|---|---|
| Ingress / API Gateway → core-app | **Rate Limiting** | Защита от всплеска 2 500 пользователей и злоупотреблений; сглаживание пиков |
| core-app → osago-aggregator (REST submit) | **Timeout, Retry** | Не залипать на submit; повтор транзиентных ошибок (идемпотентно) |
| osago-aggregator → страховые (REST) | **Timeout (60 c), Retry, Circuit Breaker, Rate Limiting (per insurer)** | 60 c — жёсткий лимит ожидания; повтор транзиентных ошибок опроса; CB отсекает недоступную/медленную страховую (её предложение просто не появится — деградация без блокировки остальных); RL — уважать лимиты API страховой и не выжигать пул опроса |
| Bulkhead (per insurer пулы опроса) | изоляция | Медленная страховая не забирает ресурсы опроса у остальных при 2 500 заявках |
| Брокер (osago-offers) | буфер + идемпотентные консьюмеры | Сглаживает всплески, повторная доставка безопасна (дедуп по offerId) |

## 5. Зависимость от мультиинстансного деплоя — ДА, учтено

- **SSE-соединение живёт на одном инстансе core-app** (это долгоживущее HTTP-соединение). Проблема —
  доставить offer-событие именно тому инстансу, что держит соединение клиента.
  - **Решение:** offer-события `osago-offers` **раздаются broadcast всем инстансам core-app**
    (каждый инстанс — свой consumer group, либо fan-out через Redis Pub/Sub). Каждый инстанс пушит
    только в те SSE-соединения, которыми владеет. Решение не зависит от того, какой инстанс держит
    соединение. LB должен поддерживать долгоживущие соединения (для SSE — sticky на время жизни
    соединения, что естественно для TCP).
- **osago-aggregator в нескольких инстансах** не должен опрашивать одну и ту же страховую дважды.
  - **Решение:** партиционирование работы по `applicationId` — команды через consumer group
    (каждая заявка обрабатывается ровно одним инстансом) и/или выборка задач опроса из БД с
    `SELECT … FOR UPDATE SKIP LOCKED`. Состояние — в общей БД (не в памяти пода).
- **core-app в нескольких инстансах**: submit и SSE stateless по данным (состояние в БД/брокере),
  поэтому горизонтально масштабируется под 2 500 пользователей.

## Итог интеграций (что новое на схеме)
| Взаимодействие | Средство |
|---|---|
| web → core-app (submit) | REST |
| **core-app → web (предложения)** | **SSE (новая стрелка)** |
| core-app → osago-aggregator (submit) | REST (Timeout, Retry) |
| **osago-aggregator → core-app (предложения)** | **события через брокер, топик `osago-offers`** |
| osago-aggregator → страховые | REST (Timeout, Retry, Circuit Breaker, Rate Limiting) |
| osago-aggregator → своё хранилище | SQL (состояние заявок/опросов) |
