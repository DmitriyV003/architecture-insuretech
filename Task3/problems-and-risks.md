# Task 3. Анализ текущей архитектуры: проблемы и риски

## Текущие взаимодействия

| # | Взаимодействие | Тип | Периодичность | Назначение |
|---|---|---|---|---|
| 1 | `core-app` → `ins-product-aggregator` | REST (pull) | каждые 15 мин | обновить локальную реплику продуктов/тарифов |
| 2 | `ins-comp-settlement` → `ins-product-aggregator` | REST (pull) | раз в сутки (ночью) | обновить локальную реплику продуктов/тарифов |
| 3 | `ins-product-aggregator` → страховые компании (5→10) | REST (fan-out) | на каждый вызов | синхронно агрегировать продукты |
| 4 | `ins-comp-settlement` → `core-app` | REST (pull) | раз в сутки | получить все оформленные за день полисы |

---

## Проблемы и риски

### P1. Синхронная агрегация fan-out к страховым компаниям
`ins-product-aggregator` на каждый запрос синхронно обходит все страховые компании и агрегирует ответ
в рамках того же запроса.
- **Латентность = самый медленный ответ.** Один медленный партнёр тормозит весь ответ.
- **Хрупкость.** Ошибка/недоступность одной компании роняет всю агрегацию → ошибки у `core-app` и
  `ins-comp-settlement` (те самые «ошибки взаимодействия» из условия).
- **Риск роста 5→10.** С удвоением числа интеграций растут суммарная задержка (tail latency) и
  вероятность, что хотя бы одна компания недоступна. Синхронная модель деградирует нелинейно.

### P2. Опрос по расписанию (polling) вместо потока изменений
`core-app` тянет данные каждые 15 мин, `ins-comp-settlement` — раз в сутки.
- **Устаревшие данные.** Реплика продуктов отстаёт до 15 мин (а у settlement — до суток). Если опрос
  упал — отставание ещё больше.
- **Пиковая нагрузка.** Периодический опрос создаёт всплески на `ins-product-aggregator` и, через
  него, на страховые компании.
- **Временная связанность.** В момент опроса `ins-product-aggregator` обязан быть доступен; иначе
  реплика не обновляется.
- **Лишняя работа.** Полный ответ тянется целиком, даже если ничего не изменилось.

### P3. Суточная REST-выгрузка оформленных полисов (settlement ← core-app)
- **Хрупкий батч.** Одна большая синхронная выгрузка раз в сутки: если `core-app` в этот момент
  недоступен/медленный — джоба падает, и её приходится повторять целиком.
- **Проблема согласованности по времени.** Полис, оформленный во время выгрузки, может быть пропущен
  или посчитан дважды (нет чёткой границы «за день»).
- **Плохо масштабируется.** С ростом числа пользователей (реклама!) дневной объём растёт, окно
  выгрузки удлиняется, риск невложиться в ночное окно повышается.
- **Нет повторной обработки.** Потеря/сбой выгрузки = потеря данных для взаиморасчётов
  (прямые финансовые потери — расчёт агентских премий).

### P4. Каскадные отказы и отсутствие развязки
Цепочка `консьюмер → aggregator → страховые` синхронна на всём протяжении. Отказ на любом уровне
распространяется вверх. Нет буфера, нет backpressure, нет истории событий для повторной обработки.

### P5. Дублирование данных без надёжного механизма синхронизации
Локальные реплики продуктов есть и в `core-app`, и в `ins-comp-settlement`, но синхронизируются
разнородными опросами. Нет единого источника изменений, нет гарантии, что реплики сойдутся.

### Влияние планируемого роста (реклама + 5 новых страховых)
- Больше пользователей → больше оформлений → тяжелее суточная выгрузка (P3), выше RPS.
- Больше страховых (5→10) → медленнее и ненадёжнее синхронная агрегация (P1).
- Всплески опроса усиливают нагрузку (P2). Каскадные отказы масштабируются вместе с системой (P4).

## Предлагаемое решение (Event-Driven, без изменения декомпозиции сервисов)

Вводим **брокер событий** (Kafka / Yandex Data Streams). Декомпозиция функций между сервисами не
меняется — меняется способ их взаимодействия.

### S1 → устраняет P1, P2, P5. Событийная рассылка каталога продуктов
`ins-product-aggregator` перестаёт быть «синхронным справочником». Он:
- опрашивает страховые **асинхронно, на своём ритме**, с Retry/Timeout/Circuit Breaker, и кэширует
  последние предложения каждой компании;
- при изменении публикует **события об изменении продуктов/тарифов** в топик `product-catalog`
  (event-carried state transfer).

`core-app` и `ins-comp-settlement` **подписываются** на топик и обновляют свои локальные реплики из
потока — в near-real-time, без опроса.
- Убирает polling (взаимодействия 1 и 2) и временную связанность.
- **Изолирует отказы страховых:** недоступность одной из 5→10 компаний делает устаревшими только её
  продукты; остальной поток идёт как обычно, консьюмеры не падают.
- **Компактируемый (compacted) топик** хранит последнее состояние по каждому ключу продукта → новый
  или восстановившийся консьюмер восстанавливает реплику из топика.

### S2 → устраняет P3, P4. События об оформлении полисов
`core-app` на каждое оформление публикует событие `policy-issued` в брокер. `ins-comp-settlement`
подписывается и **инкрементально** накапливает реестр.
- Убирает суточную REST-выгрузку (взаимодействие 4).
- Снимает проблему границы «за день» и двойного счёта — есть поток событий с идемпотентной обработкой.
- Размазывает нагрузку во времени вместо ночного батч-пика.
- Даёт возможность повторной обработки (replay) из истории топика.

### S3. Transactional Outbox — ДА (для core-app → policy-issued)
Публикация `policy-issued` — это dual-write (запись полиса в БД **и** отправка события). Чтобы не
терять и не дублировать события при сбое брокера:
- `core-app` в **одной транзакции** пишет полис и запись в таблицу `outbox`;
- **Outbox Relay** (CDC/Debezium или поллер outbox-таблицы) читает записи и публикует их в брокер.

Так гарантируется: каждое оформление порождает ровно одно событие, даже если брокер временно недоступен.
Для взаиморасчётов (деньги) это критично — Outbox обязателен именно здесь.

Для событий каталога от `ins-product-aggregator` Outbox применяем, если агрегатор персистит состояние
каталога; если он работает как кэш — достаточно at-least-once публикации с идемпотентными консьюмерами.

### S4. Идемпотентные консьюмеры
Брокер даёт доставку **at-least-once** → все консьюмеры идемпотентны: дедупликация по `event_id` /
`policy_id`, апсерт в локальную реплику/реестр. Это делает повторные доставки безопасными.

### Что остаётся синхронным (REST) осознанно
- `Веб-приложение → core-app / client-info` — клиентский трафик (детально — Task 4).
- `ins-product-aggregator → страховые компании` — внешние API, мы ими не управляем; но теперь вызовы
  вынесены из синхронного пути консьюмеров и обёрнуты паттернами устойчивости.
- `ins-comp-settlement → страховые компании` — ежемесячные взаиморасчёты.

## Итог: соответствие проблем и решений

| Проблема | Решение |
|---|---|
| P1 синхронный fan-out, хрупкость, рост 5→10 | S1: асинхронный опрос + кэш + события, изоляция отказов |
| P2 polling, устаревание, всплески | S1: поток изменений вместо опроса |
| P3 суточная выгрузка полисов | S2: события `policy-issued`, инкрементальный реестр |
| P4 каскадные отказы, нет развязки | S1+S2: брокер как буфер, развязка во времени, replay |
| P5 рассинхрон реплик | S1: единый источник изменений (compacted topic) |
| Потеря событий при dual-write | S3: Transactional Outbox + relay |
| Дубли при at-least-once | S4: идемпотентные консьюмеры |
